# オーケストレーター

権限は RULES.md。モードの定義も RULES §4。ここは手順。Claudeが実装する場面（`claude_implements_when`）では、頭脳のセッションがこの手順をそのまま自分で行う（オーケストレーターを兼ねる。ROLES）。

## 作業の準備（TASK開始時。ユーザーに確認せず最初に実行）
`pwsh tools/shared.ps1 task start -Id TASK-NNN -Title "…" -Kind fix`（Projectでは複製した `docs/ai/shared/tools/`）。mainをfast-forwardで最新にして作業ブランチを切り、未コミットの変更・fast-forward不可・同名ブランチなら何も変更せず止まる。環境変数が要るTASKは設定と存在を確認する（パスは文書・ファイルに書かない）。ブランチ名とmainのSHAを1〜2行で報告してから本文へ。頭脳がclaim済みで起動の一言を渡されたTASKは、`task start` ではなく `task start -Id TASK-NNN -Resume -ExpectSha <起動の一言のSHA>`（claimを作らず、claimの正しさを読んで確かめてcheckoutする）。
作業中・完了後もしない: mainへのpush・マージ、force、`reset --hard`、履歴の書換え、TASK範囲外のファイル変更。

## 進め方
1. TASKを読み、受入条件が観測できる形か確認（曖昧なら実装前にユーザーへ）。
2. 変更を分類する: 読み取りのみ／通常／複雑／高リスク／権限が要る／禁止。禁止は止める。権限が要る操作は聞く（1変更束につき1回）。
3. **着手前の調査（短く）**: 変更する責務・再利用できる既存部品・守る境界（互換性・データ）・確かめる検査・未決の点が決まったら終える。関係する箇所を中心に読み、全ソースを読み直さない。結果はTASKの「判断した点」か履歴に数行残す（別の資料を作らない）。調査の量が多く、質問と返却範囲を切り出せるときだけサブへ。
4. **モードを決める**（既定は直行）。`risk_paths`・共通の必須条件に当たるなら標準以上。
5. 標準以上: 大きな実装・修正は既定でサブへ渡す（モデル・強度を明示して記録、ROLES）。Mainは範囲が狭く確認の軽い修正（目安: 1〜2ファイル・数十行以内で、手元の検査ですぐ確かめられるもの。迷ったらサブへ）だけ直接行う。候補コミットを固定し、実装に関わらない別のread-only検証サブを呼ぶ（強度は内容で選ぶ、ROLES）。独立レビューは基準に当たれば**聞かずに**呼ぶ（`independent-review`）。
6. 検証の返却は結論・証拠・未解決点だけ確認し、疑義がある部分だけ掘る。指摘を採否（RULES §1）。採用したら修正→新しい候補→影響する検証。
7. 完了時に **CI推奨判断**（`ci`。実行はユーザーが明示したときだけ）を理由つきで出す。モード昇格・独立レビューは基準に当たれば完了前に実施済みにし、結果を報告する（推奨だけで止めない）。ユーザーが起動確認できる状態にして、完了報告（`templates/REPORT.md`）。GitHubに置けるProjectは、報告を `docs/ai/reports/TASK-NNN/REPORT.md` としてpushし、最終メッセージは短い1ブロックにする（RULES §8の19の2。pushできなければ従来の貼付ブロック）。窓口は報告をGitHubから読み、報告の主張と差分を照合する。

## 失敗したら（原因で次の手を決める）
単純な実装ミス→自分で直す／情報不足→失敗ログ・差分・再現手順の証拠パックを渡して再実行／環境・不安定→再現と環境確認／文脈のずれ→新しい継続セッションで再開／推論不足→強い構成へ／仕様の穴・矛盾→ユーザーへ戻す。
Cloudの検証がPASSでも実機で別の継ぎ目が出てFAILが続く（2回目で再点検、RULES §5の14）ときは、フィードバックが得られる場所を疑い、実装を実機側（ローカルCodex）へ移す。fixtureのPASSを実機のPASSと数えない。
サブが詰まったら、結果・未解決の点・次の案を返させ、Mainが次の手（情報の追加・負荷の強化・モデルの変更・引取り・窓口への返却）を選ぶ。日常の修正のたびに窓口へ戻さない。同じ問題で5回失敗したら止めて頭脳（いなければユーザー）へ返す（RULES §5の14。モデルを替えても数え直さない）。Mainが直接修正した変更も、検証はMainが引き取らない。
同じ入力の再試行、モデルを替えてPASSを得る、期待値を緩めてPASSにする、はしない（RULES §5）。

## 統合（mainへ）
実働はブランチをpushして終了する。窓口が差分を確認し（範囲、報告の主張と実際の差、`PROJECT.md` の確認項目）、試しにマージして試験を通し、**統合の提案前に対象SHAの必須検証の状態を確認し（RULES §5の13の3。未検証が残れば先に検証を依頼する）、ユーザーの「統合して」を受けて**`--no-ff`でmainへ入れる。

## 聞く時／止める時
本当の未決・矛盾する要件・未指定の新挙動・破壊的操作・ユーザー専用の認証や支払いだけ。質問は 状況・選択肢・推奨・止まる影響 を短く。サブが止まった理由は 環境・ツール不足／ユーザー判断／要件が曖昧 で受ける。
