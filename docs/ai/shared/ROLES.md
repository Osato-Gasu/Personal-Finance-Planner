# ROLES — 役割と重さ

役は**機能の名前**。誰が担うか（Codex／Claude Code）、どのモデルかは、ProjectとTASKが決める。標準・厳格モードでは別の実行にする（モードは [RULES.md](RULES.md) §4）。

| 役 | 機能 | 備考 |
| --- | --- | --- |
| オーケストレーター（Main） | TASKを読み、着手前の調査をし、実装・修正を兼ねてよい。サブを呼び、結果を確認し、ユーザーと話す窓口。**検証と独立レビューは兼ねない** | 直行では検証まで自己確認 |
| 実装 | 固定範囲内で技術を選んで実装する。要件・範囲・権限は変えられない | 通常はMainが兼ねる。量の多い定型作業はサブへ |
| 検証 | 特定コミットが基準を満たすかを、実装とは別のread-onlyな実行で確認する | |
| 独立レビュー | 別セッション（可能なら別系統）が、読み取り専用で見る。結果をレビュー記録へ | |

窓口（ユーザーと話す一本）は、既定ではオーケストレーター。Projectが頭脳セッションを窓口と定めたときは頭脳が窓口で、オーケストレーターは判断が要る点を `next_action` と報告に書いて返す（返却理由は下）。頭脳が窓口でも、簡単な確認はオーケストレーターが直接聞いてよい（範囲はRULES §8の18）。窓口が誰でも、決めるのはユーザー（RULES §1）。

ループ（実装→検証→レビュー）をCodexで回すかClaude Codeで回すかは固定しない。その時のトークン残量などで、ユーザーが選ぶ。

## 重さ（強度）
- 5段階: low < medium < high < xhigh < max。
- 通常は medium／high／xhigh から選ぶ。low・maxは理由があるときだけ。
- **検証の強度は、検証する内容（範囲・判断の難しさ・リスク）で選ぶ**。実装の強度に機械的に足さない。リスクhigh以上は最低high。基準が観測できる形（ハッシュ一致など）ならmaxにしない。
- 実装・検証の強度は**呼ぶときに明示して記録**する（不明なら依頼値、依頼値も不明ならmedium）。機械的な作業（コピー・名前変更）は下げてよい。
- 強めるときは、まず同じモデルで負荷を上げ、足りなければ上位のモデルへ。全段階を順に試さなくてよい。強めるのは未解決の部分だけで、解決済みの部分や後続に高い負荷を固定しない。Main（オーケストレーター）は自分のモデル・負荷を変えられないため、Mainが兼ねる実装で強める必要が出たら、未解決の部分だけを、モデル・負荷を明示したサブ（実装）へ渡す。サブのモデル・負荷を指定できない環境では、RULES §5の14の上限で頭脳へ返し、より強い設定での再実行を次の案に書く。
- **最上位のモデルは、証拠のそろった難問の診断に限る**（常用しない）。診断結果は修正の材料で、それだけでPASS・仕様変更にしない。使う条件と回数は`PROJECT.md`の`roles.top`。
- 具体モデルと負荷は`PROJECT.md`（Project既定）、TASKで上書き。Sharedはモデル名を書かない。予算プロファイル（saving／normal／rich）は`PROJECT.md`の`profiles`。予算が足りなくても下限は下げず、足りなければ「未検証」と報告して止まり、ユーザーに聞く。

## 返却形式（サブ・レビュー共通）
結論／対象コミット／根拠／残課題。詰まったときは、未解決の点と次の案（負荷・モデルの強化、情報の追加など）を添える。次の手はオーケストレーターが選ぶ（サブの希望は材料で、自動では承認しない）。
- 検証: PASS／FAIL／INCONCLUSIVE（理由: EVIDENCE_INSUFFICIENT・ENVIRONMENT_UNAVAILABLE・ORACLE_INSUFFICIENT・VERIFIER_TOOL_FAILURE。PASSにも失敗にもしない）。
- レビュー: NO_BLOCKING_FINDINGS／CHANGES_RECOMMENDED／BLOCKED／FAILED（レビュー側のtool・環境障害はFAILEDで指摘ではない）。
- オーケストレーターの返却理由: COMPLETED／SPEC_CHANGE_REQUIRED／USER_DECISION_REQUIRED／BLOCKED。

## 表示
- **人が見る情報と貼る情報を分ける。** コピペ用のコードブロック（頭脳へ貼る返却、Codexへ貼るプロンプト・起動の一言）には、受け手のAIが使う内容だけを書く。実行表・渡し先・経過の説明・ユーザー向けの一言は、ブロックの**外**に置き、ブロックに入れない。
- 完了・失敗・返却時は、ブロックの外に次の2つを**必ず**書く（報告ファイルへの記載だけで済ませない）。
  - **実行表**: `役割｜モデル｜負荷｜状態・結果`。1行目はMain（オーケストレーター）自身で、モデル・負荷は起動時に指定された値（強めたサブと比べるため）。続けて、呼んだサブ（実装・検証・独立レビュー・調査など）1回につき1行。失敗・再実行も1行ずつ。サブを呼ばなかったときは、Mainの行の下に「サブなし（直行・自己確認のみ）」と書く。サブのモデル・負荷は依頼した値。実測を確認できなければ「未確認」。
  - **渡し先**: このあと何をどこへ渡すか（例: `渡し先：頭脳（<Project>のClaudeセッション）へ上のブロックを貼る`／`渡し先：ローカルCodex`／`渡し先：なし`）。
- 完了・失敗・返却時の最終メッセージは、窓口（頭脳）へそのまま貼れる**1つのコードブロック**で出す。冒頭に Project名／TASK／ブランチ／対象SHA を書く（別Projectの報告との取り違え防止）。中身は 結論／返却理由／対象コミット(SHA)／根拠／残課題／CI推奨（理由）／昇格・独立レビューの推奨。Gitで受け渡すとき（RULES §8の19の2）は短い1ブロック。実行表・渡し先・ユーザー向けの文はブロックに入れない。
- ローカル操作が要る依頼は、頭脳が**ローカルCodex向けプロンプト**を1つのコードブロックで出す（RULES §8の19）。ブロックの外に渡し先を書き、ユーザー操作欄には「このプロンプトをローカルCodexへ貼る」とだけ書く。
- 最終行は`ユーザー操作：`（不要なら`ユーザー対応不要`）。未検証・未実施・CI未依頼をPASS・完了と混ぜない。

## 並列・衝突（試行）
- 並列は最大2サブ（触るパスが重ならず、共有の契約・生成物・状態にも干渉しないときのみ）。衝突は直列で直す。重なりは`touches_paths`で避ける。
